The one-line answer

The 2026-08-14 surgery cut the right lane and then lost more than it saved somewhere else. Net went from -$3.81/day to -$4.82/day. But that is the small story. The large story is in the KDP royalty export: the whole business, organic included, has not produced a royalty month outside its own pre-ads range in the three months since ads were switched on, while ad spend went from $0 to $201.62. And the reason is not bids and not price. It is that 84 of 86 advertised books have fewer than five reviews, and a book with no reviews takes impressions nobody clicks.

And the reason nobody read any of this for fourteen days is in section 6.1: the nightly integrity loop has been dead since 08-24 because Windows kills it when the laptop is on battery, and the only thing that would have reported the loop was down is the loop.

6. Right now: what is live, and two operational problems

6.1 The nightly loop has been dead for four nights, and Windows is killing it

This is the answer to "how did the account go fourteen days without anyone reading it".

daily_loop.py is the data integrity pass: it plans the pull window, pulls, pushes the warehouse, proves continuity and runs the brief. It has not completed a run since 08-24.

nightwhat brain/loop/ holdsoutcome
08-247,788 byte log and a full run recordcomplete, 114.7 min, 13/16 steps OK
08-253,370 byte log, no run recordgot as far as pull_all, which FAILED at 47s
08-26502 byte log, no run recorddied 1 second in
08-273,064 byte log, no run recordgot as far as starting Brave, then stopped
08-28502 byte log, no run recorddied 1 second in

The scheduled task's own exit code names the cause. kdp-ads-loop last returned 3221225786 = 0xC000013A, STATUS_CONTROL_C_EXIT: the process was terminated from outside, not by an error in it. And the task is registered with:

  • DisallowStartIfOnBatteries = True
  • StopIfGoingOnBatteries = True

Those are schtasks /create defaults and nobody chose them. kdp-ads-loop fires at 02:00 on a laptop. kdp-ads-daily carries the identical settings, fires at 09:00 when the machine is plugged in and in use, and returned exit code 0 on its last run. That is the pattern behind per-ASIN data being current to 08-26 while report grain and warehouse snapshots stopped on 08-24: the 09:00 task lives, the 02:00 task gets killed.

The battery setting is the best explanation on the evidence and it is cheap to act on, but the exit code proves only that something outside the process terminated it, not what. If the loop still dies after the settings change, the next thing to read is Event Viewer under Microsoft-Windows-TaskScheduler/Operational for that task at 02:00.

The loop is the thing that would have reported the loop was down. Nothing else was watching,
so a dead integrity pass is silent by construction. That is worth a separate alarm.

Fix, one command, zero risk:

` schtasks /change /tn kdp-ads-loop /rl highest powershell -c "$s=(Get-ScheduledTask kdp-ads-loop).Settings; $s.DisallowStartIfOnBatteries=$false; $s.StopIfGoingOnBatteries=$false; Set-ScheduledTask kdp-ads-loop -Settings $s" `

Do the same for kdp-scout-loop, which carries the same settings and the same 02:00 problem.
